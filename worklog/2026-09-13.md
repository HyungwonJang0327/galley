### 논의·결정 (사용자 결정 2건)

1. **carried 행을 누가 언제 만드나** — 에이전트가 두 안(재실행 Run 생성 시 vs 워커가 잡을 때)을 냈고 사용자가 **생성 시**를 골랐다. 이유: 워커가 재실행 개념을 몰라야 "워커는 오케스트레이션만" 결정이 지켜진다. 확인 UI의 `planRerun` 결과와 실제 행이 한 번의 계산에서 나온다. `resolveCarriedSources`는 같은 트랜잭션 안에서 부른다. 가드 하나 추가: 직전 Run이 실행 중이면 거부.
2. **`Run.instruction`·`Run.startStep` 컬럼을 이번에** — 지시가 없으면 Run이 왜 거기서부터 다시 돌았는지 설명 못 하고, `StepContext.instruction` 경로가 BW4까지 미검증으로 남는다. 어차피 이 PR이 스키마를 건드린다.

### 구현 (커밋 3개)

- `Run.instruction`·`startStep` + 마이그레이션 `20260913010000_run_rerun_columns`. 처음 생성된 폴더명이 UTC 타임스탬프(`20260912…`)라 기존 `20260913000000_dedupe_queue_items`보다 앞에 정렬돼 이름을 뒤로 옮겼다. `prisma format`이 다른 모델 정렬까지 바꿔 diff에 잡음이 섞이길래 되돌리고 추가분만 넣었다.
- `startRerun`(`src/run/startRerun.ts`) — 트랜잭션 하나에서 직전 Run 조회 → 가드 → `resolveCarriedSources(tx, …)` → Run+6행 생성. `resolveCarriedSources`의 파라미터를 `Prisma.TransactionClient`로 넓혔다(PrismaClient도 그대로 들어간다). 에이전트가 더한 가드 2개: `CARRIED_STEP_NOT_SUCCEEDED`(실패한 Run은 실패 단계부터만) · `INVALID_PLAN`(carried+fresh가 STEP_ORDER와 다르면 DB를 보지 않고 거절). 모델은 지정 없으면 직전 Run 것을 잇되 레지스트리·`available`은 startRun과 같게 확인. 슬러그·제목도 직전 Run 것을 잇는다(carried 산출물이 그 폴더에 있다).

### 논의·결정 (사용자 결정 3건)

1. **수정 지시된 직전 Run의 종결 상태 = `revised`**(RUN_STATUS 신설). 사용자가 조건을 하나 붙였다: **`startRerun`은 그 주제의 최신 attempt에서만** — revised된 Run에서 다시 revise하지 못하게. 기각: pendingApproval 유지+finishedAt(카운트가 finishedAt까지 봐야 함) · done(승인과 구분 안 됨).

3. **미리보기 API를 이번에.** 사용자가 GET/POST 판단을 위임: "부작용 없으니 GET이 맞지만 instruction이 길면 URL 한계. 상한을 정하고 그 이상이면 POST로." → **상한 2000자(`INSTRUCTION_MAX_LENGTH`) + POST** — 한글 2000자는 URL 인코딩 시 18KB로 8KB 한계를 넘는다. 그리고 "미리보기와 revise가 같은 planRerun+resolveCarriedSources를 부르는지 테스트 하나로 고정" → `runCommands.db.test`의 일치 테스트(세 번째 시도에서 출처 승계까지 비교).

## BW3 중단 감지·재개 — feat/worker-recovery

### 참여

- 메인 세션 단독. 착수 전 사실 확인 → 범위 질문 3건 → 사용자 결정.

### 착수 전 확인한 사실

- 회수·재개(heartbeat 30s 공백 → interrupted → 완료 단계 다음부터)는 BW2에 이미 있었고 통합 테스트도 있었다. 매 틱 `reclaimStale`이라 "기동 시+깨어날 때" 둘 다 이미 됐다.
- **단계 도중 SIGTERM이 오면 실행이 `failed`로 기록됐다.** 껍데기가 `controller.abort(new Error('SIGTERM'))`로 끊고 Mock이 `signal.reason`을 던지면 `toStepFailure`가 `STEP_FAILED`(재시도 불가)로 분류 → 즉시 실패. AbortError였어도 `ABORTED`(재시도 가능) → 3번 재시도 뒤 실패. 정상 종료가 실패를 만들고 있었다.
- **단계 도중 heartbeat가 없었다.** 시도 시작에만 써서, 30초 넘는 실제 모델 단계는 돌고 있는데도 회수된다(결정은 5s 쓰기).

### 논의·결정 (사용자 결정 3건)

1. **종료 시 클레임 반환** — 추천안에 사용자가 조건 셋을 붙였다: 반환된 단계는 시도 횟수에 세지 않는다(종료는 실패가 아니다) · 반환 직전 그 단계가 쓰던 산출물 파일을 지운다(pending으로 돌아가 처음부터 도니 반쯤 쓴 파일이 남으면 안 됨) · outcome에 `released` 추가.
2. **heartbeat** — 타이머 주입안으로 가되, 사용자가 원칙을 명확히 했다: "heartbeat는 프로세스가 살아 있다만 증명한다. 단계가 실제로 진척 중인지는 모른다. **단계별 최대 실행 시간(AbortSignal 타임아웃)은 heartbeat와 별개로 유지, 둘을 합치지 마라.**" 그리고 기각안(StepRunner 협조)의 함정을 문서에 남기라고 — "구현이 빼먹는 순간 조용히 회수된다".
3. **스모크** — CI required로 둬도 되지만 **한 번이라도 흔들리면 즉시 informational로**. 종료 코드·로그 한 줄만 단언하면 결정적이어야 정상이고, 흔들리면 테스트가 아니라 워커 종료 경로의 버그.

### 구현 (커밋 4개 + 해시 정정)

- `WorkerDeps.timers { every, after }` 주입. `runStep`이 단계 동안 `every(5s)`로 박동하고 끝나면 멈춘다. 시도마다 `after(10min)`으로 `STEP_TIMEOUT`(재시도 가능) — 구현이 `signal.reason` 대신 자기 AbortError를 던져도 `timedOut` 플래그로 타임아웃으로 기록.
- `StepRunner.discard?(ctx)` 선택 메서드(파일 쓰는 구현 B3a가 채움, Mock은 `onDiscard` 콜백). `WorkerRepo.release(runId, step, now)` — 단계 pending·startedAt null(attemptCount 그대로), 실행 interrupted·workerId null. `runOnce`: 종료 중이면 새 클레임·새 시도 안 함, catch에서 `signal.aborted`면 무엇을 던졌든 반환. 버리기가 실패해도 반환은 한다(다음 기동이 덮어쓴다).
- 테스트에서 배운 것: **마이크로태스크 개수를 세는 `await Promise.resolve()`는 runOnce 내부 await 수가 바뀌면 깨진다** → StepRunner가 "불렸다"는 순간을 기다리는 `blockingRunner.nextCall()`로 바꿨다. 슬라이스 치환하다 `fakeClock`을 지워 25개가 한꺼번에 죽은 실수 1회.
- 스모크: `bin/worker.smoke.test.ts`(임시 SQLite → `node bin/worker.ts` spawn → "워커 시작" 로그 뒤 SIGTERM → 종료 코드 0·"워커 종료"). `vitest.config.ts`로 기본 스위트에서 제외, `vitest.smoke.config.ts` + `test:smoke`. CI `smoke` 잡(Node 24). 로컬 2회 연속 통과.

- **상태 어휘 소유권을 상태 머신으로**: `RUN_STATUS`가 runQueries.ts에 있던 것을 stateMachine.ts로 옮기고 runQueries가 import한다(주석에 "값 검증은 상태 머신 몫"이라 적어 뒀던 것을 실제 구조로). 배럴·테스트 import 2곳을 따라 고쳤다.
- **`STEP_STATUS`에 `건너뜀` 추가**(요구사항 3): String 컬럼이라 마이그레이션 없음. 주석만 갱신.
- **불가 전이는 던지지 않고 `{ ok: false, code: 'NOT_PENDING_APPROVAL' }`**: CLAUDE.md §4 "던지지 말고 형태로 반환"과 같은 형태. 단계 이름 검증은 타입으로 막고, 밖에서 들어온 문자열용으로 `isStepName` 타입 가드를 따로 냈다(BW4 Route Handler가 쓸 것).

### 구현

- `nextAction(steps)`: 실패 단계가 있으면 `fail`, 없으면 `STEP_ORDER` 순서로 첫 `대기`·`실행 중` 단계를 `runStep`, 다 끝났으면 `awaitApproval`. **입력 순서를 믿지 않고** `STEP_ORDER`를 기준으로 본다. 목록에 없는 단계는 `대기`로 친다. `실행 중`을 다시 돌리는 것은 단계가 원자적이기 때문(중단 시 처음부터).

## BE14b 재실행 범위·출처 조회 — feat/rerun-cascade

### 결정 (사용자)

- `planRerun(input)` → `{ startStep, fresh, carried }`. **순수 함수 유지, DB 접근 금지.** `fresh`는 `STEP_ORDER.slice(시작)`, `carried`는 그 앞부분.
- **`carried`까지 상태 머신이 주는 이유**: 재실행 확인 UI가 "다시 도는 단계"와 "이전 결과 유지"를 둘 다 보여줘야 하는데, 한 번에 주면 호출부가 시작 인덱스를 다시 다룰 일이 없다. 계산 자체는 간단해도 **출처를 하나로 둔다.**

- **승계 규칙(핵심)**: carried의 출처는 **직전 Run이 아니라 그 결과를 실제로 생산한 Run**이다. 직전 Run의 그 행이 `fresh`면 그 Run, 이미 `carried`면 그 행의 `sourceRunId`를 그대로 승계. 승계하지 않으면 재실행을 반복할수록 출처가 한 칸씩 밀려 "이전 결과 · {원래 실행 시각}"이 실제 생산 시점과 어긋난다.

- 따라오는 것: Run에 `attempt`, `applyCommand`가 "새 Run 생성" 지시까지 반환, **산출물 경로 분리**(사람이 읽는 5개는 `posts/<슬러그>/` 루트 최신본 / Run별 부산물은 `posts/<슬러그>/runs/<runId>/`에 덮어쓰지 않고).

### ⑵ 워커는 오케스트레이션만 — `StepRunner` 뒤에 단계 내용

- **모든 단계가 모델 호출이 아니다**(썸네일=make_thumb.py, 발행정보=번들 조립). 워커에 모델 호출을 박으면 이 단계들이 예외가 되고 경계가 무너진다. 실행은 월 1–2회 상위 모델이라 비싸서, Mock StepRunner가 있어야 클레임·heartbeat·재시도·비용 기록을 **토큰 없이 CI에서** 검증한다.
- `tokens`·`cost`·`model`은 StepRunner가 돌려주고 워커는 기록만(모델 없는 단계가 있으므로 워커가 추정하지 않는다). 취소·타임아웃은 워커 소유(`AbortSignal`), 재시도 가능 여부는 에러 타입으로 알리고 정책은 워커. **워커는 ModelRegistry·SDK를 import하지 않는다.**

### ⑶ 루프 = `runOnce(deps)` + 껍데기

- "순수 함수"가 아니라 **비결정성을 전부 deps로 미는 것**이 목표(`clock`·`ids` 없이 `Date.now()`·`randomUUID`를 부르지 않는다 → heartbeat 만료를 실제 시간 없이 테스트).
- **한 tick = 한 단계.** 그래야 승인·취소·heartbeat가 tick 사이에 끼어든다. 반환 `{ outcome, stepRef? }`로 테스트가 DB를 뒤지지 않고 1차 검증하고, 껍데기는 그 값으로 대기 간격을 정한다.

### ⑷ 주제 키 = `topicId` (내 추천을 사용자가 뒤집음)

- 나는 "`QueueItem.id`는 전체 리셋으로 매번 바뀌니 `topicSlug` + attempt로 가자"고 제안했다. 사용자: **슬러그는 내용 파생이라 바뀐다** — 제목을 다듬거나 발행정보가 다른 URL 슬러그를 내면 키가 바뀌어 이전 Run이 고아가 되고 `attempt`가 1부터 다시 시작하며 승계 사슬이 끊긴다. **식별자는 내용에서 파생되지 않아야 한다.**
- 그래서 **id를 안정적으로 만드는 쪽**으로 간다: 적재를 **전체 리셋 → 줄 텍스트 매칭 upsert**, 사라진 줄은 **삭제 금지**. Run은 `topicSlug`를 키가 아니라 **그 실행이 쓴 폴더의 사실 기록**으로 계속 저장한다.
- 사라진 줄 처리: 기본 **보류 + `holdReason`**. 예외 둘 — **완료 Run이 있으면 완료 유지**(파일 유무로 확정된 상태를 뒤집지 않는다), **Run이 붙어 있으면 자동으로 내리지 말고 확인**(제목 오타 수정이 파서에겐 "삭제 + 추가"로 보여 이력이 갈라진다). 매칭은 **괄호 힌트를 뺀 제목 본문 정규화 후** 비교.

## B1g 주제 키 전환 + 큐 적재 upsert — feat/worker-loop

BW2 착수 전에 드러난 선행. "재실행 = 새 Run"과 `attempt`를 쓰려면 주제 키가 안정적이어야 하는데, 큐 적재가 **전체 리셋**이라 `QueueItem.id`가 매 로드마다 바뀌고 있었다.

### 구현 순서를 뒤집은 이유

### 스키마·키 전환 (`760c83d`)

- `Run { topicId(FK → QueueItem), topicSlug, topicTitle, attempt }`. **`topicSlug`는 키가 아니라 사실 기록** — 그 Run이 어느 폴더에 썼는지. `@@index([topicId, attempt])`.

- `findLatestRunForTopic`도 `topicSlug` → `topicId` 기준, 정렬은 `attempt` 내림차순.
- **결정을 그대로 검증하는 테스트 하나**: 제목을 바꿔 슬러그가 달라져도 `topicId`가 키라 `attempt`가 2로 이어진다(슬러그였다면 1로 리셋).

### 적재 upsert (`af28cc8`)

## 에러 처리 컨벤션 문서화 — decisions/error-handling.md

사용자가 "에러 처리 관련 컨벤션 문서가 있냐"고 물어 확인해 보니 **CLAUDE.md §4의 한 줄이 전부**였다. 반면 코드에는 이미 일관된 3층 규칙이 자리잡아 있었다 — 문서만 없었다. 새로 정하지 않고 **있는 것을 적는 쪽**으로 썼다.

### 코드에서 읽어낸 것

- **① 도메인**(pipeline) `{ ok:false, code }` 문구 없음 → **② 어댑터**(dashboard/lib) 코드→한국어 문구 + 예외를 `*_FAILED`로 감쌈 → **③ 표면**(Route Handler) HTTP 상태 매핑 → **④ 화면** `role="alert"`.
- **`throw`는 세 경계에만** 실제로 쓰이고 있었다: 프로그래머 오류(ModelRegistry 조립·Provider 밖 훅) · 외부 SDK(Anthropic·OpenAI 어댑터) · 도달 불가 분기(schedule). "던지지 말라"와 모순이 아니라 경계가 다른 것인데 그게 어디에도 없었다.
- **코드 네이밍이 세 갈래**로 이미 갈려 있었다: 상태(`BLOG_DIR_MISSING`) · 원인(`TOPIC_MISMATCH`) · `<동작>_FAILED`(예상 못한 예외를 감싼 것). 마지막 갈래가 암묵 규칙이라 도메인 코드에 섞일 위험이 있었다.

### 더한 것

- **문구가 ①이 아니라 ②에 있는 이유**를 적었다 — 도메인은 표시 문맥(화면/CLI/워커 로그)을 모른다. `@galley/ui`가 도메인 단어를 모르는 것과 같은 방향의 경계.
- **재시도 분류**(BW2 직전이라 지금 필요): 재시도 가능(네트워크·레이트리밋·5xx·타임아웃) / 영구(인증·모델 거부·프롬프트 초과) / **실패가 아닌 것**(근거 검증 `unsupported`는 표시 조건).
- **화면 없는 층**(워커·CLI): 원시 로그는 파일, 구조화된 결과는 DB.
- 기각안 3개(예외 던지고 상위에서 잡기 · 문구를 도메인에 · `AppError` 클래스 계층).

### 찾은 문제 2개

- **미결**: `RunStep`에 실패 코드·문구 컬럼을 둘지. 타임라인 실패 줄이 원인을 보여줄 수 있느냐가 걸린다 — BW2에서 정한다.

## 에러 처리 2차 — API 응답 규약 + 페이지 단위 실패 화면 (A7)

사용자가 "404 페이지 같은 UI 계획이 있냐"고 물어 확인해 보니 **`not-found.tsx`·`error.tsx`·`loading.tsx`가 하나도 없었다.** Next 기본 404가 루트 레이아웃(`<html><body>`뿐) 안에서 렌더돼 **셸 없는 검은 화면에 영어 문구**가 뜨고 있었다 — 라이트 테마·한국어·데스크톱 전용 스펙과 어긋나는 유일한 화면. 이어서 "API 에러 응답 규약도 확실히, 배포 가능성을 보고 403 같은 것도 고려"를 받았다.

### 문서 (decisions/error-handling.md 2차)

- **API 응답 봉투 고정**: `{ ok: true, data }` / `{ ok: false, error: { code, message } }` 둘뿐. 부분 성공 없음. **`ok`로 판별**(HTTP 상태만 보고 분기하지 않는다 — 프록시가 바꿀 수 있다). 204도 쓰지 않는다.
- **`error`에 스택·SQL·절대경로·환경변수를 담지 않는다** — 배포하면 그대로 밖으로 나간다. 지금 `*_FAILED` 메시지에 붙이는 예외 문구는 **배포 시 떼고 로그로만** 남긴다고 적어 뒀다.
- **상태 코드 표**: 400·404·409·500(지금 쓰는 것) + **401·403·429·503 예약**. 401=누구인지 모름(로그인하면 풀림) / 403=알지만 권한 없음(로그인해도 안 풀림) — **섞으면 화면이 "로그인하세요"를 잘못 띄운다.** **422는 쓰지 않는다**(형식 400 · 상태 충돌 409로 가른다 — 경계가 모호해진다). 모델 provider의 429는 서버가 재시도로 흡수하고 밖으로 내보내지 않는다.
- **"예약"의 뜻**: 로컬 단일 사용자라 인증이 없다(local-first · deploy-readiness "인증 자리"). 구현하지 않되 **매핑만 정해 둔다** — 나중에 각자 즉흥적으로 상태를 고르면 클라이언트 분기가 갈린다.
- **페이지 단위 실패 표**(파일 ↔ 셸 유지 여부 ↔ 비고) + 403 화면은 같은 패턴으로 나중에.

### 구현 (A7)

- **`app/not-found.tsx`**가 셸을 직접 두른다. 매칭 실패는 라우트 그룹 레이아웃을 타지 않기 때문 — 대신 셸 조립이 두 곳으로 갈리지 않게 **`_components/AppFrame.tsx`로 떼어 레이아웃과 같이 쓴다.** 이 파일 하나가 없는 경로와 `notFound()` 둘 다 받는다.
- **`(dashboard)/error.tsx`**는 클라이언트 컴포넌트라 서버 컴포넌트 `AppFrame`을 부를 수 없다 — **그룹 안에 두어 레이아웃이 위에 남게 하는 것이 셸을 지키는 유일한 방법.** 내부 사정(스택·경로·digest)은 화면에 내지 않고 `console.error`로만.
- `(dashboard)/loading.tsx`(force-dynamic이라 빈 화면 방지) · `app/global-error.tsx`(최소 그물).
- `verify:layout` 117→**125**: 404 검사 8개(TopBar 존재·높이=토큰 · 사이드바 존재·폭=토큰 · 안내 제목 · 안내가 Content 안 · 링크가 `/queue` · 가로 스크롤 없음). 검사마다 경로를 고를 수 있게 **`verify.path`**(기본 `/design`)를 뒀다.

### 실측이 잡은 버그

`<Button render={<Link href="/queue">큐로 가기</Link>} />`로 썼는데 **앵커가 비어 있었다.** `Button`이 `cloneElement(render, { className }, children)`로 children을 넘겨, Button에 children이 없으면 **Link의 자식을 `undefined`로 덮어쓴다.** 화면엔 텍스트가 보이는 것처럼 나오지만(RSC 페이로드에 문자열이 남아 `curl`엔 잡힌다) 링크는 죽는다. 올바른 형태는 `<Button render={<Link href="/queue" />}>큐로 가기</Button>` — 기존 6곳은 이 형태였고 내가 새로 쓰면서 틀렸다. `verify:layout`의 `backHref` 검사가 아니었으면 못 봤다.

## A6e "파일에서 사라짐" 확인 UI — feat/queue-missing-confirm

### 결정 (사용자)

- **"보류로 옮기기"는 `주제_큐.md`의 `## 보류`에 줄을 다시 쓴다.** 쓰지 않으면 **보류가 두 종류가 된다** — 사용자가 직접 옮긴 보류는 파일에, 대시보드가 옮긴 보류는 DB에만. 파일만 열었을 때 큐의 전체 그림이 깨지고 `## 보류`가 반쪽이 된다. **큐 파일은 대시보드 없이도 그 자체로 읽혀야 한다.**
- 쓰는 방식: 사용자가 눌렀을 때만 · **사라지기 직전 줄 원문 그대로**(괄호 힌트 포함, 제목에서 다시 만들지 않는다) · `## 보류` 끝에 덧붙이고 다른 섹션·순서는 그대로 · 쓰기 직전 파일을 다시 읽고 **임시 파일 + rename**(에디터로 열어 둘 수 있다).
- **예외**: 완료 Run이 있는 항목은 파일에 되살리지 않는다. 보류는 "앞으로 할지도 모르는 일"이라 파일에 보이는 게 쓸모 있지만, 완료는 끝난 일이고 사용자가 직접 치웠다. 이력은 대시보드가 갖고 있다.
- `missingAck`는 내 설계대로 가되 **역할이 좁아진다** — 되살리면 줄이 파일에 돌아와 다음 파싱에서 표시가 저절로 비워지므로, 실제로 필요한 경우는 **"그대로 두기" 하나뿐**이다.

### 구현 (커밋 4개)

- `feat(pipeline)` 큐 파일 쓰기를 임시 파일 + rename으로(모든 쓰기 경로가 함께 안전해진다).
- `feat(queue)` `listMissingTopics`·`restoreMissingTopicToHold`·`acknowledgeMissingTopic` + `missingAck` 컬럼.
- `fix(queue)` 아래 "실제로 돌려보고 잡은 것".
- `feat(queue)` 안내 카드(`MissingTopicsNotice`) + Server Action 2개 + 큐 페이지 배선.

### 실제로 돌려보고 잡은 것 — 이미 머지된 코드의 회귀 2건

픽스처로 서버를 띄워 "실행 붙은 주제를 파일에서 지우기"를 재현하자 두 가지가 드러났다. **단위 테스트는 전부 통과하고 있었다.**

1. **행 중복(B1g 회귀, 사용자 실제 DB에도 1건 있었다)**: 한 요청에서 **셸(`getNavCounts`)과 페이지가 병렬로 적재를 부른다.** 둘이 동시에 기존 행을 읽어 서로의 삽입을 못 보고 같은 줄을 두 번 만들었다. 전체 리셋일 때는 뒤 삭제가 앞 삽입을 덮어써 가려져 있던 문제로, 매칭 upsert로 바꾸며 드러났다. → **적재 직렬화**(`importChain`). 회귀 테스트는 직렬화를 빼면 실제로 빨개지는 것까지 확인했다.
2. **안내가 한 박자 늦게 떴다**: 큐 페이지가 `Promise.all`로 적재와 확인 대기 조회를 병렬로 돌렸는데, **사라짐 표시를 남기는 것이 그 적재**다. → 적재 뒤에 읽도록 순서를 고정.

곁가지로, 사용자 DB의 "중복"을 들여다보니 **같은 제목이 대기·후보 양쪽에 실제로 있는** 정상 데이터였다(마이그레이션이 안 지운 게 맞다). 다만 매칭이 생성 순서로만 짝지어 **섹션이 뒤바뀔 수 있었다** → 같은 섹션 항목을 먼저 고르도록 고치고 테스트 추가.

## BW2 워커 루프 — feat/worker-tick (2026-09-13)

**파이프라인이 처음으로 실제로 돌았다.** 워커가 실행을 잡아 6단계를 순서대로 끝내고 승인 대기로 넘긴 뒤 SIGTERM에 깨끗이 종료하는 것을 로그로 확인했다.

### 결정 (사용자, 착수 전 3건 + 실행 수단 1건)

- **재실행 = 새 Run** / **워커는 오케스트레이션만(StepRunner 뒤)** / **루프는 runOnce(deps)** — decisions/run-execution-model.md.
- `RunStep` 실패 기록은 **`errorCode`·`errorMessage`·`attemptCount` 셋만**. 스택·원본 응답은 Run 로그로, `retryable`은 코드에서 유도, 재시도했으면 마지막 실패만·성공하면 비운다. 코드 목록은 미리 만들지 않는다.

### 구현 (커밋 6개)

- `StepRunner`/`StepContext`/`StepResult` + `StepFailure(code, message, retryable)` + 결정적 `MockStepRunner`(실패 지점·횟수 지정 가능). `publishInfo`를 **모델 없는 단계**로 둬서 그 경로도 워커가 겪게 했다.
- `RunStep.errorCode`·`errorMessage`·`attemptCount` + 마이그레이션.
- `runOnce(deps)` — 비결정성을 전부 deps로(`clock`·`ids`), **한 tick = 한 단계**, 반환 `{ outcome, stepRef? }`.
- `createPrismaWorkerRepo` — 조건부 `updateMany`+count로 원자적 클레임, 성공 시 실패 컬럼 비우기.
- `bin/worker.ts` — 타이머(진행하면 즉시·idle이면 2초)·SIGTERM·종료만.

### 테스트가 잡은 설계 문제 3개

1. **잡는 틱과 도는 틱이 안 나뉘어 있었다.** 내 주석은 "나눈다"인데 코드는 한 틱에 둘 다 했고, 사용자가 준 outcome 목록엔 `claimed`가 있었다. 나누는 쪽으로 고치고 `claimRun`이 `justClaimed`를 함께 돌려주게 했다 — 잡자마자 승인·취소가 끼어들 틈이 생긴다.
2. **workerId를 틱마다 새로 만들고 있었다**(`ids.next()`를 runOnce 안에서). 앞 틱에 잡아 둔 실행을 자기 것으로 알아보지 못해 `idle`만 돌았다. workerId는 **프로세스의 정체성**이라 deps로 올렸다.
3. **승인 대기로 넘긴 실행을 워커가 다시 집어갔다.** `workerState`(queued/running/interrupted)만으로는 "사람 차례"를 표현할 수 없다 — **검수 상태가 `실행 중`인 것만** 집어가도록 조건을 더했다. 통합 테스트가 잡았다.

### 실행 수단 — Node 24로 (내 제안을 사용자가 정정)

`tsx` 추가를 추천했는데 사용자가 **사실 관계를 정정**했다: 타입 스트리핑은 22.18·23.6부터 기본, **24.12·25.2부터 정식**이라 Node 24면 플래그 없이 `node bin/worker.ts`가 돈다. 그리고 **Node 20은 2026-04 EOL**이라 업그레이드는 어차피 해야 하는 일이고 워커 실행은 그 부산물이다. tsx를 넣으면 Node를 올린 직후 걷어내게 된다.

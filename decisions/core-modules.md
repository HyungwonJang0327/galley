## 이유

- "AI 주도 + 핵심은 직접" 원칙. 면접에서 설명 가능한 코드를 손에 쥔다.
- 이 둘이 프로젝트의 서사(파이프라인 지휘)를 증명하는 심장.

## (a) → (a') 교체 이유 (2026-09-12)

- 사용자는 **프론트엔드 지원자**인데 직접 작성 모듈 2개가 **둘 다 서버 쪽**이었다. 면접에서 열어 설명할 코드가 본인 분야와 어긋난다.
- 상태 머신은 DB·HTTP를 모르는 순수 함수라 못 쓸 코드는 아니지만, **"무엇을 설명하고 싶은가"** 기준에서는 화면 쪽이 맞다.
- 교체 시점이 가장 싸다 — B1a는 한 줄도 쓰지 않았고 브랜치도 비어 있었다.
- (a) 상태 머신은 **pipeline 에이전트가 구현하고 사용자가 리뷰**한다(주객 전도 방지: 요구사항은 decisions/evidence-collection.md에 이미 고정돼 있어 AI가 설계를 새로 하지 않는다).
- 원래 후보 (c) Dialog는 되돌릴 수 없다 — 기각 뒤 이미 ui-engineer가 구현했다(`packages/ui/src/primitives/Dialog`).

## 기각된 대안

- **(c) `@galley/ui` Dialog(포커스 트랩·await 패턴)**: 후보였으나 2개 제한에서 제외 → ui-engineer가 구현, AI 작업 허용.
- **(a) 상태 머신을 그대로 직접 작성**: 프로젝트 서사의 심장이지만 분야가 어긋난다. 2026-09-12 교체.
- **검수 타임라인(BE13)으로 교체**: 이 도구의 정체성을 가장 잘 보여주지만 선행(B2c·BE10)이 많아 착수가 늦다.
- **핵심 모듈을 1개(모델 어댑터)로 축소**: 직접 쓴 코드가 어댑터 하나로 줄어 서사가 얇아진다.

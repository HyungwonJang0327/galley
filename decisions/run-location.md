# ② 파이프라인 실행 위치: 별도 워커 프로세스 (결정 ② 변경)

> 2026-09-09 결정 ②(`pipeline-execution-location.md` = "같은 프로세스")를 **변경**한다. 원문·기각 맥락은 그 파일에, 현행 결정은 이 파일에 있다.

## 결정

파이프라인은 **별도 워커 프로세스**가 실행한다. `apps/dashboard`는 Run을 `queued`로 **생성만** 하고 파이프라인을 실행하지 않는다.

- **워커**(`packages/pipeline/bin/worker.ts`, `pnpm --filter @galley/pipeline worker`): SQLite를 폴링해 `queued` Run을 `running`으로 잡고 단계를 돈다. **동시 실행 1개.** 잡을 때 `workerId`·`heartbeat`를 기록.
- **대시보드**: Run을 `queued`로 만들고, `running`일 때만 실행 상세를 폴링한다. **워커에 직접 신호를 보내지 않는다** — 수정 지시·승인은 **Run 상태 변경으로만** 표현하고 워커가 집어간다.
- 실행 상태(`queued`/`running`/`interrupted`)는 도메인 상태(승인 대기/완료/실패)와 **함께** Run에 얹히고, 전이는 상태 머신(B1a, 🔒 사용자 작성)이 소유한다.
- **폴링 2s · heartbeat 쓰기 5s · heartbeat 타임아웃 30s.**

## 중단·재개 (잠자기 / 재시작 / 강제 종료 구분 없음)

- heartbeat가 타임아웃(30s) 끊긴 `running`은 `interrupted`로 바꾸고, **완료된 단계 산출물 다음부터 재개**한다. 이 검사는 **워커 기동 시**와 **워커 자신이 깨어났을 때**(heartbeat 공백 감지) 둘 다 한다. 잠자기·재시작·강제 종료를 구분하지 않는다 — 전부 같은 경로다.
- **단계는 원자적**으로 취급한다: 단계 도중 끊기면 그 단계 산출물은 버리고 처음부터 다시 돈다. 단계 안에서 부분 재개는 하지 않는다.

## 로그 · 설치

- **워커 로그 = 파일**(launchd stdout/stderr). 구조화된 단계 결과(토큰·비용)는 RunStep(DB)에, 원시 로그는 파일에. DB 비대·쓰기 증폭 방지.
- **launchd plist 템플릿**(KeepAlive · 로그 경로 · .env 로드)을 `docs/worker-setup.md`와 함께 제공한다. 설치는 스크립트가 아니라 문서로. **잠자기 방지는 하지 않는다.**
- 대시보드 **TopBar 칩 옆 워커 생존 점**: 최근 heartbeat가 타임아웃 안이면 생존(초록), 아니면 중단(회색). heartbeat 한 줄 조회.

## 이유

- 실행이 Next.js 프로세스와 분리 → 앱 재시작·요청 타임아웃과 무관하게 긴 파이프라인이 돈다(온디맨드 상위 모델 실행은 길 수 있음).
- 상태(queued/running/interrupted)를 SQLite로만 주고받아 대시보드-워커 결합이 없다(단일 진실 = DB).
- 결정 ②의 "배포 시 워커로 추출"을 앞당긴 것 — 로직이 이미 `@galley/pipeline`에 있어 이동 비용이 낮다.

## 기각된 대안

- **같은 프로세스(결정 ② 원안)**: 앱 재시작·서버리스 타임아웃에 긴 실행이 끊긴다. 온디맨드 정밀 검수 실행은 길 수 있어 분리가 값을 한다.
- **대시보드가 워커에 직접 신호(IPC·소켓)**: 결합↑. 상태를 DB로만 주고받는 편이 단순·견고.
- **동시 실행 다수 + 잡 큐**: 단일 사용자·월 1~2회엔 불필요. 1개로 고정.

## 배포 시 변화

launchd → systemd / 컨테이너. **워커 코드는 그대로.**

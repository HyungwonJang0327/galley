# ③ 큐 동기화 방향: 파일이 진실(SoT), DB는 파생 캐시

## 결정

`~/Desktop/blog/주제_큐.md`가 큐의 진실(SoT)이다. SQLite는 표시·검색용 파생 캐시이자, 파일에 없는 것(실행 이력·상태 메타)의 홈이다.

- 사람은 **UI 한 곳에서만** 관리 → UI 편집이 `주제_큐.md`를 **섹션 구조(대기/후보/보류/완료)·줄 순서·완료 날짜를 유지하며 재작성**.
- Galley는 **로드 시 파일을 다시 읽어 DB를 갱신** → 스케줄이 옮긴 `완료` 등을 반영, 양방향 어긋남 0.
- 기존 수·토 스케줄은 이 파일을 계속 읽고 쓴다(Phase 2 완료까지 유지).

## 이유

- 완료 기준: "주제_큐.md와 양방향으로 어긋나지 않는다" + "사람이 직접 편집할 수 있어야 한다".
- 스케줄이 파일을 읽고 쓰므로, 파일을 버리면 스케줄이 멈춘다(→ ondemand-execution).
- "2군데서 손으로 관리"가 아니라, 관리 창구는 UI 하나. 파일은 UI/스케줄이 쓰는 공유 상태.

## 기각된 대안

- **DB가 진실, 파일 폐기**: 기존 스케줄 정지. Phase 2까지 스케줄 유지 요구와 충돌.
- **DB가 진실, 파일 내보내기 전용**: 스케줄이 파일에 되쓰는 `완료`를 재수입해야 해 결국 양방향.
- **양방향 병합 엔진**: 단일 사용자·단일 머신엔 과설계.

## 위험 / 검증

- 파일 파서/라이터는 read→수정→write→re-read가 구조상 동일해야 한다(라운드트립 테스트로 검증).
- `주제_큐.md`는 Galley가 쓸 수 있는 유일한 기존 blog 파일. 섹션 구조를 깨지 않는다.

## 적재 전략 (A4d)

로드 시 파일을 다시 읽어 DB를 갱신하는 방식은 **전체 리셋**이다: 트랜잭션 안에서 `QueueItem`을 `deleteMany`로 비운 뒤, `parseQueue` 결과를 `createMany`로 다시 넣는다.

- 파일=진실이므로 DB는 파일 상태로 통째 교체한다. 부분 diff(항목별 upsert)는 참조가 아직 없는 현 시점에 과설계다(YAGNI).
- 파서 `QueueTopic`의 **전 필드**(`title`·`category`·`completedOn`)를 `QueueItem`으로 보존한다. 큐 화면의 카테고리 필터·완료일 표시가 이 컬럼들을 쓴다.
- `order`는 섹션(status) 안에서 파서가 읽은 배열 순서를 그대로 쓴다.

### 주제 키는 id가 아니라 슬러그

전체 리셋은 매 로드마다 `QueueItem.id`(cuid)를 새로 생성한다 → **id는 재적재에 안정적이지 않다.** 따라서 Phase 1-B에서 Run(실행)이 주제를 참조할 때 **`QueueItem.id`를 FK로 쓰지 않는다.** 대신 **제목에서 파생한 슬러그**를 주제 키로 쓴다(같은 제목이면 재적재 후에도 동일 → 실행 이력이 끊기지 않는다).

- 슬러그는 파일이 진실인 큐와 DB가 진실인 실행 이력을 잇는 유일한 안정 키다.
- 이 결정은 Run 스키마(B1e) 설계 시 반영한다. A4d 단계에서는 컬럼만 추가하고 슬러그 파생은 참조가 생길 때 구현한다.

## 수동 갱신 버튼 (2026-09-12)

큐 화면 헤더에 `파일에서 다시 불러오기` 버튼을 둔다. 누르면 화면을 열 때와 같은 적재(파일→DB 전체 리셋)를 한 번 더 하고 섹션별 개수(또는 실패 사유)를 한 줄 보여 준 뒤 레이아웃 전체를 다시 그린다(Server Action + `revalidatePath('/', 'layout')`).

- **로드 시 자동 적재는 유지**한다. 버튼은 파일을 밖(Claude Code 등)에서 고친 뒤 화면을 떠나지 않고 맞추고, 맞춘 결과를 눈으로 확인하는 용도.
- AI(모델 API) 호출 없음 — Node로 파일을 읽고 파서로 나눠 SQLite에 쓰는 일뿐.
- 기각: **버튼으로만 동기화**(자동 적재 제거 — 누르기 전까지 예전 목록이 보이고 스케줄이 옮긴 `완료`가 늦게 반영된다) · **TopBar 전역 버튼**(TopBar를 [☰]·Galley·모델 칩만 두는 layout §2 결정을 바꿔야 한다).

## 배포 시 변화

다중 사용자가 되면 파일 SoT가 깨진다 → 그때 DB를 진실로 승격, 파일은 내보내기 전용으로.

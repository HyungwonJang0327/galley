# ③ 큐 동기화 방향: 파일이 진실(SoT), DB는 파생 캐시

## 결정

`~/Desktop/blog/주제_큐.md`가 큐의 진실(SoT)이다. SQLite는 표시·검색용 파생 캐시이자, 파일에 없는 것(실행 이력·상태 메타)의 홈이다.

- 사람은 **UI 한 곳에서만** 관리 → UI 편집이 `주제_큐.md`를 **섹션 구조(대기/후보/보류/완료)·줄 순서·완료 날짜를 유지하며 재작성**.
- Galley는 **로드 시 파일을 다시 읽어 DB를 갱신** → 스케줄이 옮긴 `완료` 등을 반영, 양방향 어긋남 0.
- 기존 수·토 스케줄은 이 파일을 계속 읽고 쓴다(Phase 2 완료까지 유지).

## 이유

- 완료 기준: "주제_큐.md와 양방향으로 어긋나지 않는다" + "사람이 직접 편집할 수 있어야 한다".
- 스케줄이 파일을 읽고 쓰므로, 파일을 버리면 스케줄이 멈춘다(→ ondemand-execution).
- "2군데서 손으로 관리"가 아니라, 관리 창구는 UI 하나. 파일은 UI/스케줄이 쓰는 공유 상태.

## 기각된 대안

- **DB가 진실, 파일 폐기**: 기존 스케줄 정지. Phase 2까지 스케줄 유지 요구와 충돌.
- **DB가 진실, 파일 내보내기 전용**: 스케줄이 파일에 되쓰는 `완료`를 재수입해야 해 결국 양방향.
- **양방향 병합 엔진**: 단일 사용자·단일 머신엔 과설계.

## 위험 / 검증

- 파일 파서/라이터는 read→수정→write→re-read가 구조상 동일해야 한다(라운드트립 테스트로 검증).
- `주제_큐.md`는 Galley가 쓸 수 있는 유일한 기존 blog 파일. 섹션 구조를 깨지 않는다.

## 배포 시 변화

다중 사용자가 되면 파일 SoT가 깨진다 → 그때 DB를 진실로 승격, 파일은 내보내기 전용으로.

# ③ 큐 동기화 방향: 파일이 진실(SoT), DB는 파생 캐시

## 결정

`~/Desktop/blog/주제_큐.md`가 큐의 진실(SoT)이다. SQLite는 표시·검색용 파생 캐시이자, 파일에 없는 것(실행 이력·상태 메타)의 홈이다.

- 사람은 **UI 한 곳에서만** 관리 → UI 편집이 `주제_큐.md`를 **섹션 구조(대기/후보/보류/완료)·줄 순서·완료 날짜를 유지하며 재작성**.
- Galley는 **로드 시 파일을 다시 읽어 DB를 갱신** → 스케줄이 옮긴 `완료` 등을 반영, 양방향 어긋남 0.
- 기존 수·토 스케줄은 이 파일을 계속 읽고 쓴다(Phase 2 완료까지 유지).

## 이유

- 완료 기준: "주제_큐.md와 양방향으로 어긋나지 않는다" + "사람이 직접 편집할 수 있어야 한다".
- 스케줄이 파일을 읽고 쓰므로, 파일을 버리면 스케줄이 멈춘다(→ ondemand-execution).
- "2군데서 손으로 관리"가 아니라, 관리 창구는 UI 하나. 파일은 UI/스케줄이 쓰는 공유 상태.

## 기각된 대안

- **DB가 진실, 파일 폐기**: 기존 스케줄 정지. Phase 2까지 스케줄 유지 요구와 충돌.
- **DB가 진실, 파일 내보내기 전용**: 스케줄이 파일에 되쓰는 `완료`를 재수입해야 해 결국 양방향.
- **양방향 병합 엔진**: 단일 사용자·단일 머신엔 과설계.

## 위험 / 검증

- 파일 파서/라이터는 read→수정→write→re-read가 구조상 동일해야 한다(라운드트립 테스트로 검증).
- `주제_큐.md`는 Galley가 쓸 수 있는 유일한 기존 blog 파일. 섹션 구조를 깨지 않는다.

## 적재 전략 (A4d)

로드 시 파일을 다시 읽어 DB를 갱신하는 방식은 **텍스트 매칭 upsert**다(2026-09-12 변경 — 아래 "⚠️ 전체 리셋 → 매칭 upsert").

- 파싱한 각 줄을 **정규화한 제목으로 기존 `QueueItem`과 매칭**하고, 못 찾은 줄만 새로 만든다. 정규화 = **앞뒤 공백과 괄호 힌트를 뺀 제목 본문** — `(spacehome, react-router)` 같은 힌트만 고쳤을 때는 같은 항목으로 남는다.
- **`QueueItem.id`는 처음 적재될 때 부여하고 이후 재사용하지 않는다.**
- **파일에서 사라진 줄의 `QueueItem`은 삭제하지 않는다** — Run이 붙어 있을 수 있다.

**사라진 줄 처리** — 기본은 **보류로 내리고 사유를 남긴다**(`holdReason: 'removed-from-file' | 'manual'`, 보류 탭에서 구분해 보여주면 되살릴지 판단하기 쉽다). 예외 둘:

1. **완료 Run이 있으면 완료 상태를 유지한다.** 완료 섹션의 오래된 줄을 정리하려고 지우는 경우가 있는데, 발행까지 끝난 항목을 "안 쓴 것"으로 되돌리면 안 된다. **파일의 유무로 이미 확정된 상태를 뒤집지 않는다.**
2. **Run이 하나라도 붙어 있으면 자동으로 내리지 않고 확인을 띄운다** — 큐 화면에 "파일에서 사라짐 — 보류로 옮길까요?". 줄 텍스트로 매칭하므로 **제목 오타를 고치면 파서에게는 "줄 하나 삭제 + 줄 하나 추가"로 보인다.** 그대로 두면 이력이 붙은 항목이 조용히 보류로 내려가고 새 항목이 생겨 Run 이력이 갈라진다. **Run이 없는 항목은 확인 없이 조용히 내려도 된다 — 잃을 것이 없다.**

- 파일=진실이므로 DB는 파일 상태로 통째 교체한다. 부분 diff(항목별 upsert)는 참조가 아직 없는 현 시점에 과설계다(YAGNI).
- 파서 `QueueTopic`의 **전 필드**(`title`·`category`·`completedOn`)를 `QueueItem`으로 보존한다. 큐 화면의 카테고리 필터·완료일 표시가 이 컬럼들을 쓴다.
- `order`는 섹션(status) 안에서 파서가 읽은 배열 순서를 그대로 쓴다.

### ⚠️ 주제 키 = `QueueItem.id` (2026-09-12 결정 변경)

~~전체 리셋은 매 로드마다 id를 새로 만들므로 Run은 제목 파생 슬러그를 주제 키로 쓴다.~~ → **id를 안정적으로 만들고, Run은 `topicId`로 주제를 가리킨다.**

- **슬러그는 내용에서 파생된 값이라 바뀐다.** 제목을 다듬거나 발행정보 단계가 재실행에서 다른 URL 슬러그를 내면 키가 바뀌고, 그 순간 이전 Run들이 고아가 되면서 `attempt`가 1부터 다시 시작하고 `sourceRunId` 승계 사슬도 끊긴다. "몇 번 만에 승인됐는가" 기록이 사라진다. **식별자는 내용에서 파생되지 않아야 한다.**
- **Run은 `topicSlug`도 함께 저장한다. 키가 아니라 그 실행 시점의 사실 기록이다** — 그 Run이 어느 폴더에 썼는지 알아야 하고, 슬러그가 바뀌어도 과거 Run의 폴더는 여전히 옛 슬러그다. `Run { id, topicId, topicSlug, attempt, … }`.
- `attempt`는 **`topicId` 기준**으로 센다.
- **알려진 한계**: 줄 텍스트로 매칭하므로 파일에서 **제목을 직접 고치면 새 항목**이 되고 그 주제의 시도 기록이 끊긴다. 큐 화면 편집 경로(A6c)는 id를 유지한 채 텍스트만 바꾸므로 그쪽을 권한다.

- 슬러그는 파일이 진실인 큐와 DB가 진실인 실행 이력을 잇는 유일한 안정 키다.
- 이 결정은 Run 스키마(B1e) 설계 시 반영한다. A4d 단계에서는 컬럼만 추가하고 슬러그 파생은 참조가 생길 때 구현한다.

## 수동 갱신 버튼 (2026-09-12)

### 적재를 부르는 곳 (2026-09-13)

파일→DB 적재는 **세 곳에서만** 한다: **큐 화면**·**홈**·**`파일에서 다시 불러오기`**(그리고 큐 편집 직후 재적재).

**셸(사이드바 배지)은 적재하지 않고 DB만 읽는다.** 셸은 매 요청 도는데 거기서 적재까지 하면 ⑴ 모든 라우트에서 파일 읽기·DB 쓰기가 일어나고 ⑵ 같은 요청의 페이지 적재와 **병렬로 돌아 경합**한다 — 실제로 그렇게 같은 줄이 두 행으로 생긴 적이 있다(2026-09-13, `importChain` 직렬화로 막았지만 근본 원인은 이쪽이었다).

**대가**: 큐·홈을 거치지 않고 다른 라우트만 열면 배지가 **마지막 적재 기준**이다. 진입점(`/`)이 홈이라 실제로는 거의 최신이고, 어긋나면 `파일에서 다시 불러오기`로 맞춘다. 홈은 이미 읽은 섹션을 배지에 그대로 넘겨(`getNavCounts(preloaded)`) 화면과 배지가 **같은 순간의 값**을 보게 한다.

큐 화면 헤더에 `파일에서 다시 불러오기` 버튼을 둔다. 누르면 화면을 열 때와 같은 적재(파일→DB 전체 리셋)를 한 번 더 하고 섹션별 개수(또는 실패 사유)를 한 줄 보여 준 뒤 레이아웃 전체를 다시 그린다(Server Action + `revalidatePath('/', 'layout')`).

- **로드 시 자동 적재는 유지**한다. 버튼은 파일을 밖(Claude Code 등)에서 고친 뒤 화면을 떠나지 않고 맞추고, 맞춘 결과를 눈으로 확인하는 용도.
- AI(모델 API) 호출 없음 — Node로 파일을 읽고 파서로 나눠 SQLite에 쓰는 일뿐.
- 기각: **버튼으로만 동기화**(자동 적재 제거 — 누르기 전까지 예전 목록이 보이고 스케줄이 옮긴 `완료`가 늦게 반영된다) · **TopBar 전역 버튼**(TopBar를 [☰]·Galley·모델 칩만 두는 layout §2 결정을 바꿔야 한다).

## 섹션 이동 규칙 (2026-09-12, AN5·A6b·A6c)

큐 행 ⋮에서 대기↔후보↔보류를 옮긴다. UI 편집이 파일을 재작성한다는 위 원칙의 첫 구현.

- **완료는 이동 대상이 아니다**(사용자 결정). 되돌리면 완료일(`YYYY-MM-DD`)이 사라지고 스케줄이 쓴 기록과 어긋난다. 완료 탭 행에는 ⋮를 두지 않는다.
- **대기·보류로 옮기면 맨 아래**(사용자 결정). 기존 순서를 건드리지 않고, 대기 맨 위 "다음 실행"(layout §4) 자리가 밀리지 않는다. 순서 변경은 A6a(DnD).
- **후보로 옮기면 카테고리 없는 구간(첫 `###` 앞)의 끝**. 맨 아래에 넣으면 직전 `###` 소제목이 그 항목의 카테고리가 되어(파서 규칙) 재적재 때 없던 카테고리가 생긴다.
- **후보를 떠나면 카테고리를 잃는다**. 카테고리는 후보 섹션의 `###` 소제목이라 다른 섹션에서는 표현할 자리가 없다(파일 형식을 바꾸지 않는다는 제약의 결과).
- **동시 변경 방어**: 이동 입력은 `from`·`to`·`index`(섹션 내 위치, 카테고리 필터 전 기준)·`title`. 쓰기 직전 파일을 **다시 읽어** 그 위치의 제목이 다르면 `TOPIC_MISMATCH`로 파일·DB 어느 쪽도 건드리지 않는다(스케줄이나 편집기로 그새 바뀐 경우).
- 이동 성공 후에는 재적재(전체 리셋)로 DB를 파일 상태에 맞춘다.

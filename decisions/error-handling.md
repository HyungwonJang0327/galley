# 에러 처리 컨벤션 (도메인 → 어댑터 → 표면 → 화면)

CLAUDE.md §4의 한 줄("던지지 말고 형태로 반환")을 층별로 푼다. **새로 정하는 규칙이 아니라 코드에 이미 자리잡은 것을 적는다** — 지금까지 문서가 없어 층 경계와 `throw` 허용 범위가 암묵이었다.

## 원칙

**예상된 실패는 값이다.** 호출부가 분기해야 하는 실패는 던지지 않고 돌려준다. 던지는 것은 "여기서 더 갈 수 없다"는 프로그래머 오류·외부 경계뿐이다.

## 층

| 층                                         | 형태                                                            | 문구                        | 예                                             |
| ------------------------------------------ | --------------------------------------------------------------- | --------------------------- | ---------------------------------------------- |
| **① 도메인** (`packages/pipeline`)         | `{ ok: true, … } \| { ok: false, code }`                        | **없다.** 코드만.           | `moveQueueTopic` · `startRun` · `applyCommand` |
| **② 어댑터** (`apps/dashboard/lib`)        | `{ ok: true, data } \| { ok: false, error: { code, message } }` | 코드 → **한국어 문구** 매핑 | `queue-move` · `run-start` · `queue-data`      |
| **③ 표면** (Route Handler · Server Action) | 같은 형태 + **HTTP 상태** 매핑                                  | ②의 문구 그대로             | `POST /api/runs` (400·404·409·500)             |
| **④ 화면** (컴포넌트)                      | `result.ok`로 분기                                              | ②의 `message`를 그대로 렌더 | 큐 화면 · 행 ⋮ 메뉴                            |

**왜 문구가 ①이 아니라 ②인가**: `packages/pipeline`은 서버 전용 도메인 계층이고 표시 문맥(화면·CLI·워커 로그)을 모른다. 같은 코드라도 큐 화면에서는 "다시 불러온 뒤 시도해 주세요", CLI에서는 다른 문장이 맞다. `@galley/ui`가 도메인 단어를 모르는 것과 같은 방향의 경계다.

**어댑터의 의무 둘**: ⑴ 도메인 코드를 **빠짐없이** 문구로 매핑한다(`Record<Failure, string>`이라 코드가 늘면 타입이 깨져 알려준다) ⑵ 예상 못한 예외를 `try/catch`로 감싸 `*_FAILED` 코드로 바꾼다 — **예외가 표면 밖으로 새지 않는다.**

## `throw`가 허용되는 경계

1. **프로그래머 오류** — 잘못 조립하면 기동조차 하면 안 되는 것. `ModelRegistry` id 중복·기본 모델 미등록, `useSidebarCollapse`를 Provider 밖에서 호출.
2. **외부 SDK 경계** — 모델 어댑터 안(Anthropic·OpenAI). 그 밖으로 새지 않게 **호출부가 반드시 감싼다.**
3. **도달 불가 분기** — 타입으로는 가능하지만 논리상 없는 경우(`schedule.ts`).

그 외에는 던지지 않는다. 특히 **셸 레이아웃이 부르는 것은 절대 던지면 안 된다** — 한 곳이 실패하면 모든 화면이 500이 된다(CLAUDE.md 함정 절).

## 에러 코드 네이밍

`UPPER_SNAKE`. 세 갈래로만 쓴다.

- **상태**: `BLOG_DIR_MISSING` · `TOPIC_NOT_FOUND` · `MODEL_UNAVAILABLE` — 무엇이 없거나 쓸 수 없다.
- **원인**: `TOPIC_MISMATCH` · `INVALID_SECTION` · `NOT_PENDING_APPROVAL` · `RUN_ALREADY_ACTIVE` — 규칙에 걸렸다.
- **`<동작>_FAILED`**: `QUEUE_MOVE_FAILED` · `RUN_START_FAILED` — **예상 못한 예외를 감싼 것**(②의 catch). 도메인 코드로는 쓰지 않는다.

코드는 화면에 그대로 보이지 않는다(사람이 읽는 것은 `message`). 로그·테스트·HTTP 상태 매핑의 키다.

## API 응답 형태 (③)

**응답 봉투는 두 가지뿐이다.** 부분 성공은 없다 — 실패면 아무것도 바꾸지 않고 실패만 돌려준다.

```jsonc
// 성공
{ "ok": true, "data": { … } }
// 실패
{ "ok": false, "error": { "code": "RUN_ALREADY_ACTIVE", "message": "이 주제는 아직 끝나지 않은 실행이 있습니다." } }
```

- **`ok`로 판별한다.** HTTP 상태만 보고 분기하지 않는다(프록시·런타임이 상태를 바꿀 수 있다).
- **`error`에는 `code`와 `message`만.** 스택 트레이스·SQL·파일 절대경로·환경변수 값을 담지 않는다 — 배포하면 그대로 밖으로 나간다. 원인 상세는 서버 로그에.
- `message`는 **사람이 읽는 한국어 한 문장**, `code`는 기계가 읽는 키다. 화면은 `message`를 그대로 쓰고 `code`로 분기한다.
- 본문 없는 성공(204)은 쓰지 않는다 — 언제나 `{ ok: true, data }`로 통일해 호출부가 한 갈래로 읽는다.

## HTTP 상태 매핑 (③)

매핑은 `Record<ErrorCode, number>`로 **한곳에** 두어 코드가 늘면 타입이 깨지게 한다.

| 상태    | 언제                                                                                              | 코드 예                                                          |
| ------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **400** | 본문·파라미터가 형식에 안 맞음                                                                    | `INVALID_BODY` · `EMPTY_TITLE` · `UNKNOWN_MODEL`                 |
| **401** | 누구인지 모름(미로그인·토큰 만료) — **예약**                                                      | `UNAUTHORIZED`                                                   |
| **403** | 누구인지는 알지만 권한이 없음 — **예약**                                                          | `FORBIDDEN`                                                      |
| **404** | 대상이 없음                                                                                       | `TOPIC_NOT_FOUND` · `RUN_NOT_FOUND`                              |
| **405** | 그 메서드를 안 받음                                                                               | (핸들러가 export하지 않으면 Next가 준다)                         |
| **409** | 형식은 맞지만 지금 상태와 충돌                                                                    | `RUN_ALREADY_ACTIVE` · `NOT_PENDING_APPROVAL` · `TOPIC_MISMATCH` |
| **422** | **쓰지 않는다** — 형식 오류는 400, 상태 충돌은 409로 가른다. 경계가 모호해진다                    |                                                                  |
| **429** | 레이트리밋 — **예약**(모델 provider의 429는 서버 안에서 재시도로 흡수하고 밖으로 내보내지 않는다) | `RATE_LIMITED`                                                   |
| **500** | 예상 못한 예외를 감싼 것                                                                          | `*_FAILED`                                                       |
| **503** | 의존 대상이 지금 없음 — **예약**(워커 정지 등)                                                    | `WORKER_UNAVAILABLE`                                             |

**401과 403을 가르는 기준**: _누구인지 모르면_ 401(로그인하면 풀린다), _알지만 안 되면_ 403(로그인해도 안 풀린다). 섞으면 화면이 "로그인하세요"를 잘못 띄운다.

**"예약"의 뜻**: 지금은 로컬 단일 사용자라 인증이 없다(decisions/local-first.md · deploy-readiness.md "인증 자리"). **구현하지 않되 매핑만 정해 둔다** — 나중에 각자 즉흥적으로 상태를 고르면 클라이언트 분기가 갈린다.

### 배포 때 다시 볼 것

- **`requestId`**: 서비스로 배포하면 응답에 상관관계 id가 필요하다. 봉투에 자리를 더할지는 그때 정한다(지금 넣으면 쓰지 않는 필드가 는다).
- **메시지 노출 범위**: 지금 `*_FAILED`의 `message`에 예외 문구를 붙여 로컬 디버깅을 돕는다(`실행을 시작하지 못했습니다: SQLITE_BUSY`). **배포 시에는 이 뒷부분을 떼고 로그로만 남긴다.**

## 재시도 분류 (워커)

단계 실행 실패는 **재시도 가능 여부를 에러 타입으로** `StepRunner`가 알리고 **정책(횟수·간격)은 워커**가 정한다(decisions/run-execution-model.md).

- **재시도 가능**: 일시적 실패 — 네트워크·레이트리밋·5xx·타임아웃.
- **영구**: 입력·설정 문제 — 인증 실패, 모델 거부(refusal), 프롬프트 초과, 파일 없음.
- **실패가 아닌 것**: 근거 검증의 `unsupported`는 **표시 조건**이다. 실패 경로로 보내지 않는다(evidence-collection 요구사항 2).

## 단계 실패 기록 (2026-09-13)

`RunStep`에 실패 정보를 남긴다. **최소한으로** — 컬럼 셋뿐이다.

| 컬럼                      | 쓰임                                                        |
| ------------------------- | ----------------------------------------------------------- |
| `errorCode` (nullable)    | **안정적인 분류 키.** UI 문구 매핑과 재시도 가능 여부 판단. |
| `errorMessage` (nullable) | 타임라인에 **그대로 띄울 한 줄**. 사람이 읽는 문장.         |
| `attemptCount`            | 이 단계를 몇 번 시도했는지 — "3번 시도 후 실패"를 보여준다. |

**두지 않는 것**

- **스택·원본 응답은 컬럼에 넣지 않는다.** 그 Run의 로그(`posts/<슬러그>/runs/<runId>/`)에 남기고, 타임라인 실패 줄을 펼치면 그 로그를 보여준다. **행은 가볍게 유지한다.**
- **`retryable` 별도 컬럼을 두지 않는다.** `errorCode`에서 유도하는 함수 하나로 충분하다. 같은 코드가 상황에 따라 재시도 가능하기도 하고 아니기도 하면 그때 컬럼을 만든다.

**기록 규칙**

- 워커가 재시도했다면 **마지막 실패만** `RunStep`에 남긴다. 중간 시도의 에러는 로그에만.
- **성공하면 세 값을 모두 비운다.** 이전 실패의 흔적이 성공한 단계에 남으면 안 된다.
- `errorCode` **초기 목록은 미리 정하지 않는다.** `StepRunner`가 에러 타입을 돌려주기 시작하는 BW2에서 **실제로 나오는 것만** 추가한다 — 미리 만든 코드 목록은 대부분 쓰이지 않는다.

**기각**: _로그 파일에만 남기기_ — 타임라인이 원인을 못 보여줘 **재실행 판단이 불가능**해진다(무엇을 고쳐 다시 돌릴지 알 수 없다).

## 화면이 없는 층 (워커·CLI)

문구를 사람에게 보여줄 자리가 없다. **원시 로그는 파일**(launchd stdout/stderr), **구조화된 결과는 DB**(RunStep)에 남긴다 — decisions/run-location.md. 워커는 코드·메시지를 로그에 남기고, 화면은 나중에 DB에서 읽어 그린다.

## 페이지 단위 실패 (④)

인라인 알림으로 안 되는 경우 — 페이지 자체가 성립하지 않을 때. **셸(TopBar·Sidebar)은 살아 있어야 한다.** 사용자가 막다른 곳에 갇히지 않고 다른 화면으로 바로 갈 수 있어야 하고, 셸이 사라지면 앱이 죽은 것처럼 보인다.

| 상황                      | 파일                              | 셸                             | 비고                                              |
| ------------------------- | --------------------------------- | ------------------------------ | ------------------------------------------------- |
| 없는 경로 · `notFound()`  | **`app/not-found.tsx`**           | `AppFrame`으로 직접 두른다     | 매칭 실패는 라우트 그룹 레이아웃을 타지 않는다    |
| 렌더 중 예외              | **`app/(dashboard)/error.tsx`**   | 그룹 레이아웃이 유지돼 자동    | 클라이언트 컴포넌트. `reset()`으로 다시 시도      |
| 로딩                      | **`app/(dashboard)/loading.tsx`** | 같음                           | 셸 라우트가 전부 `force-dynamic`이라 빈 화면 방지 |
| 루트 레이아웃 자체가 실패 | **`app/global-error.tsx`**        | 불가(`<html>`부터 다시 그린다) | 최후의 그물. 최소한으로                           |
| 권한 없음(403)            | 같은 패턴으로 추가                | `AppFrame`                     | **지금은 인증이 없어 만들지 않는다**              |

- **`AppFrame`은 한 곳**(`(dashboard)/_components/AppFrame.tsx`)에 있고 레이아웃과 `not-found`가 같이 쓴다. 셸 조립이 갈라지면 404만 모양이 달라진다.
- `error.tsx`는 **클라이언트 컴포넌트**라 서버 컴포넌트인 `AppFrame`을 부를 수 없다. 그룹 안에 두어 레이아웃이 위에 남게 하는 것이 유일한 방법이다.
- 페이지 단위 실패 화면에도 **되돌아갈 길**을 둔다(404 → 큐로 가기, error → 다시 시도).

## 화면 표시 (④)

- 실패 문구는 **`role="alert"`**로 낸다(스크린 리더가 즉시 읽는다). 지금 큐 화면·행 메뉴·드래그 목록이 모두 이 방식이다.
- **성공은 조용히**, 실패만 말한다. 실패해도 **아무것도 바꾸지 않는다**(`revalidatePath`는 성공했을 때만).
- **되돌릴 방법을 문구에 넣는다** — "다시 불러온 뒤 시도해 주세요"처럼.

## 기각된 대안

- **예외를 던지고 상위에서 잡기**: 어떤 실패가 가능한지 타입에 드러나지 않아 호출부가 분기를 빠뜨린다. 셸 레이아웃에서는 화면 전체가 죽는다.
- **문구를 도메인(①)에 두기**: 표시 문맥을 모르는 층이 문장을 갖게 되고, CLI·워커에서 화면용 문장이 로그에 남는다.
- **에러 클래스 계층(`AppError extends Error`)**: 직렬화(Route Handler 응답)와 판별 유니온이 이미 하는 일을 클래스로 다시 하는 것. 던지지 않기로 한 이상 이점이 없다.

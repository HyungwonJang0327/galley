# 실패한 실행의 재실행: 승인 대기와 같은 규칙, 실패 상태는 유지

## 결정

**`failed` 실행에도 수정 지시(재실행)를 받는다.** 승인 대기와 같은 경로(계획 미리보기 → 확인 → `startRerun`으로 새 Run)다. 승인은 받지 않는다.

- 실패 Run의 상태는 **`failed` 그대로**(종결 상태, `finishedAt` 유지). `revised`로 바꾸지 않는다 — "다음 시도가 있는가"는 같은 주제의 더 큰 `attempt`로 본다.
- **시작 단계 기본값 = 실패한 단계**(첫 번째 `succeeded`가 아닌 단계). 그 앞 단계는 고를 수 있고(그 단계부터 전부 다시), 뒤 단계는 고를 수 없다 — `startRerun`의 `CARRIED_STEP_NOT_SUCCEEDED` 가드가 거절하고 화면은 그 항목을 비활성으로 보인다. "단계 자동"(지시의 근거·커밋 키워드)은 승인 대기에서만 — 실패에서는 키워드가 있어도 실패 단계보다 뒤로 가지 않는다.
- **수정 지시는 비워도 된다**(실패 원인을 밖에서 고친 뒤 "그냥 다시"). 승인 대기에서는 지금처럼 필수.
- `running`·`interrupted`(워커가 스스로 재개)·`done`·`revised`는 그대로 거절(`NOT_PENDING_APPROVAL` 코드 유지 — 문구는 앱 어댑터가 상태별로).

## 이유

- 성공한 앞 단계를 이어받아야 비용이 실패 단계에만 든다. 발행정보(썸네일 Chrome 없음)처럼 모델과 무관한 실패가 흔하다.
- 재실행 흐름이 하나다(승인 대기와 같은 함수) — 새 경로를 만들지 않는다.
- 실패 이력이 남는다: 목록 배지 "실패"·단계 행의 오류 코드가 그대로라 "몇 번 실패했나"를 셀 수 있다.

## 기각된 대안

- **실패 Run을 `revised`로 종결**: 상태 규칙은 하나가 되지만 실패 사실이 상태에서 사라지고 `revised`의 정의(승인 대기에서 수정 지시)가 넓어진다.
- **재실행 대신 새 실행 시작**(실행 시작 Dialog): pipeline 변경은 없지만 앞 단계를 전부 다시 돌리고, 수정 지시를 실을 자리가 없으며, 실패 Run과 새 Run이 `sourceRunId`로 이어지지 않는다.

## 영향

- decisions/run-execution-model.md §1 "수정 지시를 받은 Run의 종결 상태 = `revised`"는 **승인 대기에서 받은 경우**로 한정된다 — 실패에서 받은 경우는 `failed` 유지(갱신 이력에 표시).
- `applyCommand`는 `failed` + `revise`를 받고 `status: failed`(불변)·`rerun`을 돌려준다. `reviseRun`은 실패 Run의 `finishedAt`을 덮지 않는다.
- 화면(ActionBar): 실패에서 재실행 활성·승인 비활성(사유), 단계 Select 기본값 = 실패 단계·뒤 단계 비활성, 지시 입력은 선택.

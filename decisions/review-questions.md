# 확인 질문 — 실행이 물을 곳을 골라 묻고, 답을 받은 곳만 고친다 (MVP 포함)

## 결정

- **MVP에 넣는다**(2026-11-22 사용자 "이 기능도 MVP에 포함"). 데스크톱 스케줄이 하던 "글을 뽑고 → 확인이 필요한 2~3군데를 골라 묻고 → 답을 반영해 글을 고친다"를 Galley 안에서 한다. 지금은 `[확인 필요]` 주석·근거 검증 목록·자유 글 수정 지시라는 재료만 있고, 추리기·답 입력·부분 수정이 없다.
- **질문은 규칙으로 고른다**(모델 호출 없음). 기각: 모델이 고름(실행당 호출 1회 추가), 본문 단계가 같이 냄(근거 검증 결과가 반영되지 않는다).
- **답은 이전 본문을 주고 그 부분만 고친다.** 기각: 지금처럼 전체를 다시 씀(답하지 않은 문장까지 달라진다).

## 질문 고르기

- 본문 프롬프트에 주석 형식을 고정한다: `<!-- [확인 필요] <사용자에게 물을 질문 한 문장> — <왜 확인 못 했는지 한 줄> -->`. 질문 추출은 이 형식을 파싱해 **앞부분(질문)만** 쓴다.
- 우선순위: `[확인 필요]` 주석 → 근거 검증의 "근거 없음" 주장. 같은 종류 안에서는 본문 순서.
- 상위 3개만 질문으로 올린다. 넘치는 것은 버리지 않고 **"그 외 N건"으로 접어** 같이 보여 준다.
- 질문마다 **앵커**(주석이 있던 문단 — 근거 없음 주장은 그 문장의 문단)를 같이 저장한다. 답 반영이 쓴다.

## 답 반영

- 답 종류는 셋: **채움 / 모름(현행 유지) / 삭제(그 문장 빼기)**.
  - 모름: 모델 호출 없이 주석만 제거하고 확정한다.
  - 삭제: 코드로 처리한다(모델 호출 없음).
  - 채움: 모델을 부르는 유일한 경우.
- 채움은 **이전 본문 전체 + 질문·답 + 앵커**를 주고 전체 본문을 다시 출력하게 한다. 받은 뒤 이전 본문과 **문단 단위 diff**를 떠서, 바뀐 문단이 앵커 문단과 그 앞뒤 1문단 밖에도 있으면 실패 → 1회 재시도 → 또 실패하면 승인 대기로 올린다.
- 이 diff 검사는 **승인 게이트 모듈 쪽**에 두고 단위 테스트를 붙인다.
- 뒤 단계는 영향 있는 것만:
  - 근거 검증은 항상 재실행.
  - 링크드인·Zenn은 전체 재생성이 아니라 **이전 결과 + 바뀐 문단**을 주고 같은 방식(패치 + diff 검사)으로 고친다.
  - 삽화·썸네일은 기본 건너뛴다. 바뀐 문단이 `[삽화]` 주석 바로 앞뒤일 때만 "삽화 다시 만들까요?"를 확인 질문으로 올린다.
- "이전 산출물을 입력으로 받는 단계"는 todo RH5(재실행 입력에 이전 본문을 넣을지)와 같은 변경이다 — **RH5를 이 작업(RH13)에 합쳐 닫는다.**

## 진행 방식

- 작업 단위 하나가 끝날 때마다 커밋 → /log → 보고 → 다음 진행 여부를 묻고 멈춘다(CLAUDE.md §9 그대로).

## 착수 결정(2026-11-22 사용자 — 선택지 넷 모두 1번 + 보충)

- **반영 단위 — 새 실행 + 단계별 방식**: 답 반영도 새 실행(N+1차)으로 남긴다. 단계마다 "다시 만듦 / 이전 결과 유지 / 고침(패치)" 중 하나가 되고, 삽화·발행정보는 뒤 단계여도 "이전 결과 유지"가 될 수 있게 상태 머신을 넓힌다(지금 carried는 시작 단계 앞에만 있다). 기각: 같은 실행을 제자리에서 고침(고치기 전 본문·단계 기록이 사라진다).
- **발행정보 — 단계 전체를 유지**: 소개·태그·썸네일을 이전 것 그대로. 어긋나면 발행정보부터 재실행. 기각: 글만 다시 만들고 썸네일 그림만 유지.
  - **예외**(보충): 바뀐 문단(채움·삭제 모두)이 `[삽화]` 주석 바로 앞뒤 문단이면 "삽화 다시 만들까요?" 질문과 함께 **발행정보 단계도 재실행 대상으로 올린다**(삽화 목록의 삽입 위치 문장이 틀려지므로). **썸네일 PNG는 그래도 유지한다** — 이 경우에만 발행정보 단계에 "그림은 이전 것" 길이 필요하다.
- **두 번 실패 — 이전 본문 그대로 + 미반영 표시**: 범위 밖이 바뀐 글이 승인본이 되지 않는다. 기각: 두 번째 출력을 채택하고 경고.
  - 미반영 표시는 **질문 단위**로 남기고, 다음 재시도 때 **그 질문·답을 그대로 다시 쓸 수 있게** 한다(보충).
- **코드만 수정 — 모름만이면 뒤 단계 없음, 삭제가 있으면 검증 + 패치**: "모름"은 주석만 지워 글 내용이 그대로라 모델 호출 0회. "삭제"가 하나라도 있으면 근거 검증을 다시 돌리고 링크드인·Zenn을 패치한다.
  - "삭제"로 뒤 단계가 돌 때도 범위 검사는 **같은 규칙(앵커 ±1문단)** 을 적용한다(보충).

## 구현 메모(에이전트 — 결정 아님)

- 문단 = 빈 줄로 나눈 덩어리. 코드 펜스는 안에 빈 줄이 있어도 통째로 한 문단. 줄 번호는 1부터(근거 검증의 `line`과 같은 기준).
- 앵커 = 그 항목이 있는 문단 번호 + 줄 번호. 질문 목록은 DATA_DIR 산출물 파일로 둔다(posts에 복사하지 않는다).
- 옛 형식 주석(`—` 없이 한 덩어리)은 내용 전체를 질문으로 읽는다.
- 단위: ① 문단 나누기·질문 추출·주석 형식 프롬프트 ② 문단 diff 검사(승인 게이트 쪽) + 모름·삭제의 코드 처리 ③ 상태 머신의 단계 방식(패치·뒤 단계 유지)과 답 반영 실행 만들기 ④ 본문 패치(채움 — 재시도·미반영) ⑤ 링크드인·Zenn 패치 ⑥ 질문 파일 산출 + 실행 상세의 질문·답 화면·API ⑦ "삽화 다시 만들까요?"와 발행정보 예외.

- 단계 방식(단위 ③): `RunStep.origin`에 `patched`(이전 결과를 고쳐 만든 단계)를 더했다 — 산출물은 이 Run의 것이고 `sourceRunId`는 고칠 대상을 만든 Run. 답 반영 계획(`planAnswerRerun`)은 근거 수집·삽화·발행정보를 유지, 본문을 고침, 글 내용이 바뀌면 근거 검증은 다시·링크드인·Zenn은 고침(안 바뀌면 셋 다 유지).
- 질문·답은 `Run.reviewAnswers`(JSON, `review/answerSet.ts`)에 질문(앵커 포함)과 함께 둔다 — 고치는 단계가 질문 파일을 다시 찾지 않고, 미반영 답을 다음 시도가 그대로 다시 쓴다. 채움 글 상한 2,000자, 한 번에 50건.
- 답 반영(`answerRun`)은 **승인 대기에서만** 받는다(실패 Run에는 이어받을 뒤 단계가 없다). 고치는 길이 아직 없는 단계에 고침 입력이 오면 `PATCH_UNSUPPORTED`로 멈춘다 — 조용히 처음부터 다시 만들지 않는다(단위 ④⑤가 본문·링크드인·Zenn을 열었다).

- 본문 고침(단위 ④, `steps/velogPatch.ts`): 코드 답을 먼저 반영하고, 채움의 자리는 **그 뒤 본문에서 다시 찾는다**(`locateQuestion`). 모델에는 이전 본문 전체 + 고칠 문단 원문·질문·답 + 어투만 준다(근거 묶음은 주지 않는다 — 채움의 사실은 사람의 답). 출력이 범위 밖을 바꿨거나 비었거나 잘렸으면 반려 → 1회 재시도 → 이전 본문 유지. 채움 여러 건은 한 번의 호출로 고치고, 반려되면 그 호출의 채움 전부가 미반영이다. 모델이 남긴 답한 질문의 주석은 코드가 지운다.
- 뒤 단계 고침(단위 ⑤, `steps/derivedPatch.ts` — 링크드인·Zenn 공용): 본문에서 바뀐 곳은 고치기 전·후 본문의 문단 diff로 구한다(`[확인 필요]` 주석은 걷어내고 견준다 — 주석만 지운 문단은 바뀐 것이 아니다). 바뀐 곳이 없으면 모델 없이 이전 결과 그대로. 있으면 이전 결과 전체 + 바뀐 곳(전·후 문단) + 어투를 주고 전체를 다시 받는다. 파생 글은 본문과 문단이 1:1이 아니라 **앵커를 미리 알 수 없어**, 같은 규칙(한 곳 = 문단 ±1)을 **곳 수**로 건다(`checkPatchPlaces`): 이 글에서 바뀐 문단을 덮는 ±1 창의 수가 본문에서 바뀐 곳 수 이하여야 한다. 반려 → 1회 재시도 → 이전 결과 유지. 결과는 `<단계>-patch.json`(`patched`·`unchanged`·`kept`)에 남기고, `kept`여도 단계는 성공이다(본문의 미반영과 같은 방식 — 화면이 보인다). Zenn은 frontmatter(제목·`published: false`)를 모델에 주지 않고 그대로 다시 붙인다.
- 결과 파일 `review-result.json`(DATA_DIR, 본문 단계 산출물): `{version, baseRunId, applied[], unapplied[{id, code}]}`. 미반영 코드: `QUESTION_UNKNOWN`·`COMMENT_NOT_FOUND`·`SENTENCE_NOT_FOUND`·`ANCHOR_NOT_FOUND`·`PATCH_OUT_OF_SCOPE`·`PATCH_OUTPUT_INVALID`.
